# 公开仓库红线门禁：个人语境词的提交/推送硬阻断

- Date: 2026-09-14
- Status: Complete
- Scope: ① 第二轮全库清理，把公开仓库里残留的个人语境词扫到 0；② 建立提交/推送前硬阻断的红线门禁，
  让个人语境词无法再进公开仓库。

## Context

上一轮「公众门面中性化」之后仍有两个问题：

1. **清理动作本身成了泄漏源。** 那一轮的 change record 逐类枚举了被移除的词
   （"指向……的表述"），等于把要移除的词又写回公开仓库；CHANGELOG 里也照抄了一遍。
2. **暴露面不止一类语境。** 上一轮只清「个人身份/学业交付」一类，而「私人事务语境」
   （个人对外材料、私人路线相关）的用词从未纳入清理范围，散落在 12 份历史记录与规划文档中，
   数量比前一类更多。

第二轮全库扫描的实测：**19 个文件、32 处命中行**。

### 2. 红线门禁（三道 hook + 本地词表）

| 组件 | 位置 | 说明 |
|---|---|---|
| 词表 | `.git/info/redline-words.txt` | **本地文件，不入库、不推送**。格式 `C:<词>`（CJK 子串匹配）/ `W:<word>`（ASCII 词边界匹配） |
| 扫描器 | `.git/info/redline-guard.sh` | 共用实现，支持 `commit` / `commit-msg` / `push` / `audit` 四种模式 |
| 钩子 | `.git/hooks/{pre-commit,commit-msg,pre-push}` | 三道分别扫暂存内容、提交信息、待推送差异 |

设计要点（每条都对应一个真实的踩坑）：

- **词表必须放在版本库之外。** 若把词表提交进仓库，词表本身就泄漏了要防的词——自指悖论。
  因此词表与扫描器都放 `.git/info/`（永不进版本库），需要跨机器复用时从私有材料库取回。
- **只扫新增行（`^+`），不扫删除行。** 否则"清理敏感词"的提交本身会把被删的旧行扫出来而被自己的门禁拦下。
- **ASCII 词按词边界匹配。** 否则该英文词会误命中同词根的 `hypothesis` —— 实测波及 20+ 个文件。
- **不能用管道把内容喂给扫描器。** `cmd | scan` 会让被调函数跑在子 shell 里，命中计数不会传回父进程，
  表现为"报出命中却 exit 0"——门禁看起来在工作，实际全放行（实测踩到）。必须用进程替换 `< <(...)`。
- **失败关闭（fail-closed）。** 词表缺失时阻断操作并提示取回，而不是静默放行。
- **变量后紧贴全角字符必须加花括号。** `"（$range）"` 在本机 bash + `C.UTF-8` 下会把全角的字节
  并进变量名，报 `range）: unbound variable`，门禁在**命令展开阶段**就崩掉 ——
  表现为 pre-push 首次推送直接失败（实测踩到）。必须写成 `"（${range}）"`。
- **豁免开关 `ALLOW_REDLINE_BYPASS=1`**，命中时打印醒目警告后放行；仅用于确知安全的例外。

## Verification

- `redline-guard.sh audit`（全库只读巡检）：**✓ 全库 0 命中**。
- 清理由门禁自己验收：改写过程中门禁曾拦下一次提交——当时新写的记录正文里出现了一个红线词，
  已改写后通过。空转放行的可能性因此被排除。
- 纯文本改动：本批只动文档与一处代码注释，无逻辑变更。全量 `go test ./...` 结果与改动前一致
  （`scripts/load-probe.mjs` 的注释不参与编译）。

## Risks / Notes

- **词表是本地文件，不进版本库。** 换机器或重装时需从私有材料库的 `materials/guards/`
  取回词表与扫描器，否则门禁无法工作。
- **git 历史仍留有既往暴露。** 本次只保证 HEAD 与后续提交干净；早期提交的内容与提交信息里
  仍有私人语境词。历史重写需要 force push、会改变全部 SHA，并使既有版本锚点提交失效，
  **未执行**；是否执行需独立决策。
- **模糊词未纳入词表。** 例如英文 `Star` 与 GitHub star 同形，纳入会大面积误伤正常用法；
  这类词靠人工把关，是门禁的已知缺口。
- 门禁是**本地**防线：它约束本机提交与推送，不约束他人或网页端的直接提交（本仓库为单人维护，风险可控）。

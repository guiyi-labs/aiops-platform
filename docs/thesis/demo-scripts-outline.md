## 链路一：故障发现 → 规则诊断 → 受控修复

**场景**：生产 Namespace 中的 Deployment 持续 CrashLoopBackOff，运维人员从资源工作台发现问题并完成闭环修复。

**入口**：Web UI → 侧边栏「集群」→ 选择目标集群 → 「工作负载」→「Pods」列表页

### 演示步骤

1. **展示多集群资源工作台**
   打开目标集群 Pods 列表，列内 Status 列出现红色 `CrashLoopBackOff` 徽标；
   点击 Pod 名称进入详情抽屉，展示「状态」「重启次数」和「上次终止原因」字段（`OOMKilled` 或 `Error`）。

2. **查看 Pod 事件流**
   在详情抽屉切换到「Events」标签，确认 `BackOff` 类型事件已呈现时间戳和 Message；
   说明：事件来自 Kubernetes API Server，不经平台数据库缓存，实时性可验证。

3. **发起规则诊断**
   点击详情抽屉右上角「诊断」按钮；平台以该 Pod 为目标调用诊断引擎，
   规则 ID（如 `pod/crash-loop`）、严重级别（`critical`）、触发条件和证据快照在结果页呈现。

4. **阅读证据时间线**
   诊断结果页展示「事实证据」区：包含 `restartCount`、`lastState.terminated.exitCode`、
   关联 Event 引用和资源 `resourceVersion`；说明规则结论绑定不可变证据快照，
   与 AI 摘要区（可选增强，标注「AI 解释」标签）明确分隔。

5. **（可选）展示 AI 解释增强**
   切换「AI 解释」面板，展示引用式摘要：每句推断标注对应证据编号；
   说明：关闭或降级时规则诊断链路不受影响，AI 仅补充自然语言解读。

6. **受控修复：dry-run rollout restart**
   点击「处置」→ 选择「Rollout Restart」→ 系统先执行 Dry-Run 预演：
   页面显示「预演成功，目标 Deployment: `<name>`，操作: `rolloutRestart`」；
   未点击「确认执行」前集群状态不变。

7. **二次确认并执行**
   点击「确认执行」后系统提交幂等操作计划（Idempotency Key 可见）；
   Kubernetes API 返回后处置历史列表新增一行，Status 为 `succeeded`。

8. **验证幂等重放与审计**
   再次点击相同「Rollout Restart」并确认：系统返回同一计划 ID，
   处置历史不新增第二行；打开「审计」页筛选本次操作，
   展示操作者、资源、结果、请求 ID 字段（凭据与请求体已脱敏）。

### 证据锚点

| 验证对象 | UI 元素 / 指标 / 文本 |
|---|---|
| 故障可见性 | Pods 列表 Status 列 `CrashLoopBackOff` 红色徽标 |
| 规则诊断 | 诊断结果页规则 ID `pod/crash-loop`、严重级别 `critical` |
| 证据不可变 | 证据快照中 `resourceVersion` 与集群 API 实时值一致 |
| 受控写路径 | 处置历史行 Status `succeeded`、Idempotency Key 唯一 |
| 幂等保护 | 重放后处置历史行数不增加，返回同一计划 ID |
| 审计可追溯 | 审计记录包含操作者、资源、请求 ID，凭据字段为 `[redacted]` |

### 翻车预案

- **kind 集群不可达**：切换至 `.artifacts/e2e-kind/` 最新脱敏 JSON，
  明确说明这是上次真实验收留存的历史证据，规则逻辑不变。
- **Pod 尚未进入 CrashLoopBackOff**：等待控制器重试（通常 30–60 s），
  不临时修改规则或伪造页面；期间可先演示审计和处置历史静态内容。
- **AI Provider 不可用**：直接演示确定性诊断，
  正好说明"规则为主、AI 为辅"的降级设计，无需道歉。
- **rollout restart 未修复问题**：此为预期现象；明确说明该步骤目的是
  验证受控写路径，而非声称能修复错误镜像或 OOM 根因。

## 链路二：事故响应闭环

**场景**：监控告警触发后系统自动创建事故，团队在事故工作区协作处理并完成复盘导出。

**入口**：Web UI → 侧边栏「告警」→「告警列表」

### 演示步骤

1. **查看告警列表与抑制规则**
   打开告警列表，展示当前活跃告警；
   点击「抑制规则」标签，展示至少一条已生效的 Inhibit Rule（如父告警 firing 时子告警被抑制），
   说明平台实现了 Alertmanager 风格的降噪机制，而非仅转发原始告警。

2. **从告警创建事故**
   选中目标告警，点击「创建事故」；事故工作区页面自动打开，
   展示标题、严重级别、触发告警来源引用、SLA 倒计时定时器（初始状态）。

3. **展示事故工作区核心指标**
   切换到「时间线」视图，展示 MTTA（首次应答时间）和 MTTR（修复时间）
   的实时计算值；SLA 倒计时条显示剩余时间（绿/黄/红）；
   说明这三项指标均由平台基于时间戳实时计算，不依赖外部 APM 服务。

4. **打开 Runbook 链接**
   在事故详情页点击「Runbook」链接，展示对应处置文档（外链或内嵌）；
   说明 Runbook 绑定在告警路由规则中，事故创建时自动关联。

5. **触发升级通知**
   点击「升级」按钮，选择通知渠道（如 Webhook 或邮件）；
   展示通知记录列表，确认一条 `delivered` 状态的升级通知已落库。

6. **结案并导出复盘**
   将事故状态流转为「Resolved」；点击「导出复盘」，
   系统生成 Markdown 文件（含时间线、MTTA/MTTR 数值、关联告警、处置摘要）；
   在浏览器或编辑器中展示导出文件的前 20 行，确认结构与模板一致。

### 证据锚点

| 验证对象 | UI 元素 / 指标 / 文本 |
|---|---|
| 告警抑制 | 告警列表「被抑制」状态列 + 抑制规则详情页 Inhibit Rule 行 |
| SLA 倒计时 | 事故工作区顶部 SLA 进度条颜色与剩余时间数值 |
| MTTA / MTTR | 时间线视图中两项指标的时间戳差值（分钟级精度） |
| Runbook 关联 | 事故详情页 Runbook 字段非空，链接可点击 |
| 升级通知 | 通知记录列表一行 Status `delivered`，渠道、时间戳可见 |
| 复盘导出 | 下载文件扩展名 `.md`，内容首行为 `# Postmortem:` 标题 |

### 翻车预案

- **通知渠道 Webhook 超时**：展示通知记录列表中的 `failed` 行，
  说明平台记录了投递失败，重试机制和幂等性有日志可查；
  不需要现场强制重发，失败记录本身就是可审计的证据。
- **导出文件空白或格式错误**：提前在 `.artifacts/` 保存一份历史复盘导出样本，
  切换展示，说明这是上次真实事故演练的输出。
- **MTTA/MTTR 数值为 0 或异常**：说明这是演示环境时间戳精度问题，
  展示时间线视图中的原始时间戳字段进行人工验证。

## 链路三：SLO 超燃预警 + 告警降噪

**场景**：SLO 错误预算消耗速率超过阈值，平台聚合多信号并降噪后展示全貌。

**入口**：Web UI → 侧边栏「可观测性」→「SLO」→「SLO 总览」

### 演示步骤

1. **展示 SLO burn rate 总览大盘**
   打开 SLO 总览页，展示每条 SLO 的当前 Error Budget 消耗百分比和 Burn Rate 趋势；
   高亮至少一条 Burn Rate 超过告警阈值的 SLO 条目（红色/橙色标注）；
   说明：Burn Rate 由平台基于真实 Metrics 序列实时计算，非写死阈值。

2. **下钻查看 Error Budget 详情**
   点击超燃 SLO 条目，进入详情页：展示过去 7 天 Error Budget 消耗曲线、
   当前滑动窗口评估值、剩余预算（百分比和预计耗尽时间）；
   说明这三项来自 M41 SLO 模块，由 Node/Pod 真实 Metrics 七天精确序列驱动。

3. **展示关联告警与路由**
   切换到「告警路由」页，展示已为该 SLO 配置的告警路由规则：
   接收器（Receiver）、过滤条件、分组键（group_by）和静默时间窗口；
   说明去重（deduplication）机制：相同标签集的告警在分组窗口内合并为一条。

4. **打开事件驾驶舱**
   进入「事件驾驶舱」页，展示与 SLO 超燃时间窗口对齐的多信号关联视图：
   Kubernetes Event、告警触发记录、指标异常点三类信号在同一时间轴对齐；
   点击任一信号节点，展示其来源、时间戳和关联规则 ID。

5. **展示指标历史下采样归档**
   进入「Metrics」→「历史」页，展示已下采样压缩的长周期指标序列（M114 特性）；
   选择超过 7 天前的时间范围，确认数据仍可查询（精度降低但未丢失）；
   说明下采样归档减少存储压力同时保留趋势可查性。

6. **验证告警静默与降噪效果**
   回到「告警列表」，切换「已静默」标签，展示在分组窗口内被合并抑制的重复告警；
   展示降噪前后告警条数对比（如原始 12 条 → 聚合后 3 条），
   说明平台实现了 Alertmanager 风格的 group_wait / group_interval 降噪逻辑。

### 证据锚点

| 验证对象 | UI 元素 / 指标 / 文本 |
|---|---|
| Burn Rate 超阈值 | SLO 总览页红色/橙色 Burn Rate 徽标 + 具体数值（如 `3.2x`） |
| Error Budget 曲线 | 详情页 7 天折线图，曲线斜率可见加速段 |
| 路由去重配置 | 告警路由页 `group_by` 字段非空，`group_wait` 时间值可见 |
| 多信号对齐 | 事件驾驶舱时间轴至少 2 类信号（Event + 告警）在同一时间窗口可见 |
| 历史归档查询 | Metrics 历史页 7 天前查询返回数据，精度标注可见 |
| 降噪效果 | 「已静默」标签下告警数量 < 原始触发数量 |

### 翻车预案

- **SLO 总览无超燃条目**：提前在 `deploy/demo-scenarios/` 中加载
  `slo-burn-demo.yaml` 注入高错误率流量，触发超燃状态；
  或直接展示截图 `docs/thesis/screenshots/` 中预存的 SLO 超燃截图并说明。
- **Metrics 历史页查询超时**：说明历史归档基于本地 PostgreSQL，
  演示环境数据量有限；展示 `.artifacts/` 中预导出的 JSON 指标样本。
- **事件驾驶舱信号数量为零**：确认演示集群的 kind 环境已运行足够长时间；
  切换时间范围为「过去 30 分钟」；若仍无数据，展示历史截图并口头说明关联逻辑。
- **告警路由页路由列表为空**：提前通过 UI 或 API 创建至少一条 Receiver 和 Route；
  若现场来不及，展示 API 响应 JSON（`GET /api/v1/alert-routes`）作为替代证据。

## 通用注意事项

1. **演示环境就绪检查**：正式演示前运行 `.\scripts\demo-up.ps1`，
   确认 Compose 三服务 healthy 且 kind 集群 Nodes Ready。
2. **证据备份原则**：每条链路至少准备一份 `.artifacts/` 或 `docs/thesis/screenshots/`
   的静态备份，确保网络或集群故障时有据可查。
3. **AI 标注一致性**：所有 AI 输出（解释、摘要）必须在 UI 中标注「AI 解释」标签，
   答辩时主动说明其可选增强属性，与确定性规则主链路区分。
4. **凭据与数据脱敏**：投屏时确认密码输入框已遮挡，审计页凭据字段显示 `[redacted]`。
5. **时间控制建议**：三条链路合计建议控制在 12–15 分钟，
   每条链路约 4–5 分钟；证据锚点验证环节建议留 30 秒供答辩委员记录。
